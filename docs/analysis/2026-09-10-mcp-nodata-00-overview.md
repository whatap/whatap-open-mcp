## 하나의 사건, 세 층의 결함

신고된 단일 응답은 서로 독립적인 세 결함이 겹친 결과다.

1. **카탈로그에 실행 불가 쿼리가 실려 있다.** `<% AGENT %>` 등 yard 템플릿 마커가 치환되지 않은 채 저장되어 있고, MCP 저장소 전체에 `<%` 를 처리하는 코드는 0건이다 (`src/data/mxql-catalog.ts` 제외 시 grep 0 hits). 그대로 서버에 전송된다 — `src/tools/yard.ts:873-886`.
2. **서버가 알려준 오류를 코드가 삭제한다.** 오류행 검사가 `result.length === 1 && errorMsg.includes("not found")` 로 이중 제한되어(`src/tools/yard.ts:915-916`) 통과하지 못하고, 이어지는 `!r["_head_"] && !r["error"]` 필터가 그 행을 메타데이터로 폐기한다(`:937`).
3. **남은 자리를 추측이 채운다.** `buildNoDataResponse` 가 `isError` 를 세우지 않고, 신고자가 본 원인 3개는 응답 내용과 무관한 하드코딩 상수다 — `src/utils/response.ts:191-194`.

MCP 프로토콜 계층은 무결하다. `isError` 는 `src/mcp/server.ts:109` → `protocol.ts:92-97` 로 그대로 전달되므로 수정 지점은 전부 도구 계층이다.

## 세 요청의 관계 (겹치지 않음)

- 요청 1은 **22개 오류 응답**을 살린다. 75개 빈 배열에는 무효.
- 요청 2는 **100개 마커 경로 전체**를 실행 전에 차단한다. 마커 없는 경로의 빈 결과에는 무효.
- 요청 3은 위 둘을 모두 통과한 **정상 실행·0건** 상태를 다룬다. `response.ts:191-194` 의 단정문은 요청 1·2 어느 쪽도 건드리지 않으므로, 둘만 반영하면 신고된 그 문구는 그대로 남는다.

권장 순서: 1(핫픽스 가능) → 2(차단 범위 최대) → 3(문구·에코).

## 각 보고서의 새 사실 (신고 내용을 넘어선 것)

**req1** — 같은 오류 삼킴 양식이 7곳에 복제되어 있다. `src/tools/log.ts:292-350` 이 최악으로 오류행 검사 자체가 없다. 반면 `src/tools/promql.ts:137-160` 은 이미 정답 패턴(배열 전체 탐색, 메시지 내용과 무관한 `isError`)이라 수정은 이를 공용 헬퍼로 승격하는 일이다.

**req2** — 마커 경로는 카탈로그에 **두 번** 실려 있다. `src/main/resources/...` 100개 + `target/classes/...` 100개 = 931 엔트리 중 200개(21.5%). 생성기 필터가 `endsWith('.mql')` 뿐이라(`scripts/generate-catalog.ts:43-47`) yard 소스 트리와 그 빌드 산출물을 함께 삼켰다. `mxql/` 트리(699 엔트리)에는 마커 경로가 0개다 — 결함 전체가 잘못 적재된 모듈 하나에서 나온다.
- 호출자가 마커를 채울 수 없다: 100개 중 97개가 `$param` 선언이 아예 없고, 나머지 3개도 `$stime`/`$etime`(kind:auto)뿐이다. → 사전 차단이 옳고, 매개변수 안내로는 해결되지 않는다.
- path 엔드포인트 우회도 답이 아니다: 이 "경로"들은 다른 yard 모듈의 **파일시스템 경로**라 200+[] 가 404 로 바뀔 뿐이다.
- 발견 경로가 진짜 문제다: `search="transaction"` 은 18건을 돌려주는데 **100% 마커 경로**다. useragent 100%, httpc 92%. LLM이 동작하는 경로를 고를 수 없다.
- `describe_query` 는 실패할 호출을 적극 권한다 — `parser.ts:96-100` 이 `$param` 만 인식해 마커가 안 보이므로 `parameters:[]` 가 "인자 불필요"로 읽히고, `yard.ts:690-698` 이 그 경로의 실행 예시를 출력한다.

**req3** — 실행된 MXQL의 가용성은 분기마다 다르다. text 분기는 `rawMxql`(`yard.ts:875`)이 살아 있어 그대로 에코 가능, path 분기는 서버가 `.mql` 을 전개하므로 최종 실행문을 알 수 없어 카탈로그 원문을 "server-expanded" 로 명시 첨부해야 한다, PromQL 분기는 `OPENMX ${query}`(`client.ts:124`)로 재구성 가능. `client.ts` 반환 타입 변경은 불필요하다.
- 경로 이중 표기: 카탈로그 키는 전부 `mxql/` 접두사인데(`"path": "v2/..."` 0건 vs `mxql/v2/...` 340건) 툴 설명(`yard.ts:738-744`, `descriptions.ts:19`)은 접두사 없는 표기를 권한다. 시킨 대로 부르면 `describeMql` 이 null 을 반환해 path 엔드포인트로 빠지고 카테고리 힌트가 영영 뜨지 않는다. 같은 저장소의 `descriptions.ts:281` 이 이미 접두사를 벗기고 있어 이중 표기를 인지하고 있음이 증명된다.
- `mesh.ts:349-366` 은 `Promise.all` 이라 4개 서브쿼리 중 하나만 실패해도 성공한 3개가 버려진다 → `allSettled` 권장.

## 착수 전 반드시 확인할 함정 2개

1. **`tests/mcp-protocol/test.ts:102`** 는 `text.includes("No data") || text.length < 50` 을 실패 신호로 쓴다. 새 문구로 바꾸면 테스트가 깨지는 게 아니라 **조용히 항상 통과**한다. 문구 변경과 같은 커밋에서 갱신해야 한다.
2. **회귀 테스트 후보 "검색 결과에 실행 불가 경로가 없을 것" 은 오늘 `transaction` 에서 실패한다.** 마커 경로를 숨기면 그 검색이 0건이 되기 때문이다. `mxql/` 트리에 대체 가능한 transaction 통계 경로가 있는지 먼저 확인이 필요하다.

## 공통 미확인 (토큰 필요)

- 실제 와이어 본문 미캡처. "배열 안 오류 행" 은 소거법 역추론이다.
- 오류 필드명이 `error` 외에 존재하는지, `msg` 를 오류 키로 넣으면 로그 응답에 오탐이 생기는지.
- 75(빈 배열)/22(오류) 분해의 경로별 매핑은 재현하지 않았다 — 신고자 수치를 그대로 인용했다.
- `<% %>` 치환 주체가 yard 저장소 어디인지 미확인. MCP에 치환을 복제하는 것은 틀린 데이터로 조용히 답하게 되므로 반대한다.

## 범위 경계

여기 어느 항목도 PLAT-854(문법 오류 MXQL에 200+빈배열)를 대체하지 않는다. MCP 안에서 빈 배열을 오류로 간주하는 것은 정상적인 0건과 구분 불가하므로 명시적으로 반대한다. MCP 측 수정은 Yard 수정과 병렬 진행 가능하다.
